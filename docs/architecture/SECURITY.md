# Security

Status: Accepted (Phase 0). Updated for Phase 5b as built (2026-11-22: RLS, online payments, couriers, documents;
PHASE-5B-CONTRACT §12 S19–S39); Phase 6 custom domains added 2026-11-22 (T30, PHASE-6-CONTRACT §9 S40–S52). Applies to all apps. Every control below has a named owner area and a required test.
Operations (roles, secrets, workers, rollback): `docs/deployment/RUNBOOK.md`.

## 1. Assets
Tenant business data (orders, customers' PII — names, phones, addresses), merchant credentials (passwords,
tokens, payment-gateway keys, courier keys), money flows (order totals, payment status, SaaS billing),
domain-to-store mapping, platform admin access, availability of storefronts.

## 2. Actors & trust boundaries
| Actor | Entry point | Trust |
|---|---|---|
| Anonymous shopper | Storefront (any host) → Next.js → API storefront endpoints | Untrusted |
| Merchant user (owner/admin/staff) | Merchant SPA → `/api/v1/stores…` and tenant routes with Bearer + `X-Tenant-Id` | Authenticated, scoped to memberships, role-limited |
| Platform admin | Super-admin SPA → `/api/v1/admin` | Privileged; MFA required; IP/Access-restricted |
| Storefront server | API with `X-Storefront-Key` | Trusted service, but host claim still validated |
| Payment / courier / Cloudflare | Webhooks → `/api/v1/webhooks/{provider}/{route_key}` (5b: `sslcommerz`, `bkash`, `steadfast`, `pathao`; `redx` 404 until verified); gateway browser returns → signed `/api/v1/payments/return/{provider}/{payment}` | Untrusted: the route key only picks the account; money and courier status changes always re-query the provider |
| Gotenberg (PDF renderer) | Internal network only, called by the `documents` queue worker | Trusted service, but it renders merchant/shopper text: input is escaped plain text with no URLs |
| Malicious merchant | Their own tenant + theme config + uploads | Assume hostile towards other tenants and shoppers |

## 4. Baseline controls
- **Transport:** HTTPS only, HSTS (`max-age=31536000; includeSubDomains` on platform domain; not preload for custom domains).
- **Headers:** API: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, no CORS except
  `app.`, `admin.` origins (exact list, credentials false). Storefront CSP:
  `default-src 'self'; img-src 'self' https://cdn.storeplix.com data:; script-src 'self' 'nonce-…' <payment SDK hosts>; frame-ancestors 'self' https://app.storeplix.com` (editor preview).
  SPAs: strict CSP, `frame-ancestors 'none'`.
- **Session (SPA):** until Phase 4.7, Sanctum token in `sessionStorage`. From 4.7: httpOnly host-only session cookie on the
  SPA origin (same-origin API proxy), absolute 7-day expiry (D3), no token in JS storage; on 401 the SPA clears
  local state and redirects to `/login` ("Your session expired, please sign in again"). See PHASE-4-CONTRACT §7.
- **Authorization:** Policies per model; `Gate::before` only for `super_admin` inside admin routes. Permission matrix
  (owner/admin/staff) in ADR 0005.
- **Validation:** Form Requests; `tenant_id`, `status` of money objects, `total_amount` never mass-assignable.
- **Admin impersonation:** read-only by default, time-boxed 30 min, banner in UI, audit-logged with reason.
- **Dependencies:** Dependabot/Renovate, `composer audit` and `pnpm audit --prod` in CI (fail on high).
- **Backups:** encrypted PITR; restore drill quarterly; backups in separate account/bucket.
- **Data protection:** customer PII export/delete endpoints per tenant (Phase 8); logs exclude PII bodies.
- **Secrets (5b):** production secrets come only from the secret manager: `APP_KEY`, `INTEGRATION_CREDENTIALS_KEY`
  (+ `_PREVIOUS_KEYS` during a rotation), the three DB role passwords, `STOREFRONT_API_KEY`, `REVALIDATE_SECRET`,
  `GOTENBERG_USERNAME`/`PASSWORD`, SMS/mail keys, and from Phase 6 `CLOUDFLARE_API_TOKEN` and `DOMAINS_ASK_KEY`. Every default in `docker-compose.yml` and
  `infrastructure/docker/.env.example` (including the committed `INTEGRATION_CREDENTIALS_KEY` and the role passwords
  equal to the role names) is DEV-ONLY and public. Give each process only the DB credentials it needs: web and
  tenant workers the app role, scheduler/console the admin role, the migrate job the owner role (QA 5b-1 I-2; compose
  gives all three to every API container, which is acceptable only locally).
- **Production boot refusals (5b, 6):** `PAYMENTS_FAKE=true`, `COURIERS_FAKE=true` or `DOMAINS_FAKE=true` with `APP_ENV=production`;
  in production also an empty `CLOUDFLARE_API_TOKEN` or `CLOUDFLARE_ZONE_ID` (Phase 6);
  `TENANCY_RLS=true` with the app user equal to the owner user, the admin user equal to the app user, or an app role
  that is a superuser or `BYPASSRLS` (checked on connect). `/api/v1/dev/*` routes are never registered in production.
- **Incident response:** Sentry alerts → on-call; operational runbook `docs/deployment/RUNBOOK.md` (DB roles, workers,
  secrets, rollback incl. the RLS emergency switch-off); a security-incident playbook follows in Phase 9.
